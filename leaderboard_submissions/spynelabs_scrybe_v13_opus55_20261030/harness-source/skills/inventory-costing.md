- Follow the task's algorithm exactly when it gives one (layer order, tie-breaks, which purchases are available to a sale, partial fills, fallbacks). If your own consistency check disagrees with the stated algorithm on this data, keep the stated algorithm and report the count of affected rows.
- FIFO / LIFO as range overlap: give each purchase layer a cumulative range per item (`sum(qty) over (partition by item order by received_at, id rows unbounded preceding)` → `[cum - qty, cum)`) and each sale a cumulative demand range in sale order (`[cum - qty, cum)`); the allocated quantity is the overlap `greatest(0, least(p_end, s_end) - greatest(p_start, s_start))`, and COGS is `overlap * unit_cost`. FIFO orders layers oldest first; LIFO newest first, which for a perpetual system means only layers received on or before the sale date, so it is not a single global range: allocate per sale against the layers still available at that time.
- Perpetual vs periodic: perpetual allocates at each sale using inventory on hand at that moment; periodic allocates once per period against the period's pool. Decide from the task's wording and use one consistently.
- Weighted average cost: running `sum(qty * cost) / sum(qty)` of on-hand units, recomputed after each receipt; sales do not change the average. A fallback to weighted average applies only to the rows the task names (for example sales with no matching layer).
- Conservation checks: per item, allocated units = sold units that have layers available; remaining units = purchased - allocated, never negative; ending value = sum over remaining layer quantities × their cost. Count sales with unallocated quantity separately instead of dropping them.
- Multi-currency: check the direction of the rate table (`from_currency → to_currency`) before joining; if only USD→X rates exist, a X→USD amount is `amount / rate`. Use the rate effective on or before the transaction date (`asof join` or `qualify row_number() over (partition by txn order by rate_date desc) = 1` on `rate_date <= txn_date`), and keep the original-currency amount alongside the converted one.
- When the live data never exercises a rule (no overlap between purchase and sale items, no partial fills), test the logic on a few hand-made rows in a scratch query and say so; do not ship logic that has only ever produced empty or constant output.
