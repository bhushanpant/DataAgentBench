- Run dbt from the project directory: `cd <project> && dbt ...`. dbt reads `profiles.yml` from the project directory when it has one (or from `DBT_PROFILES_DIR` / `~/.dbt`); the profile name must match `profile:` in `dbt_project.yml`.
- dbt: `dbt run -s model_a model_b`, `dbt build -s model` (run + tests), `dbt compile -s model` (compiled SQL in `target/compiled/...`), `dbt ls -s +model` (lineage), `dbt show -s model --limit 10`, `dbt parse`, `dbt deps` (installs the packages in `packages.yml`). Add `--quiet` or pipe through `tail -40` to keep output short. Never run a bare `dbt run` on a project with hundreds of models; select what you need.
- Read compiled SQL and error locations instead of guessing. dbt errors name the model and line; open that file.
- `sql "<query>" [max_rows]` (harness script on PATH) runs a read-only query against the project's warehouse (DuckDB opened read-only; Snowflake through the profile's connection). `sql "describe <schema>.<table>"` lists columns and types; `sql "select table_schema, table_name from information_schema.tables order by 1, 2" 500` lists relations. A trailing `LIMIT n` sets the number of rows shown. Output that ends in `[TRUNCATED: ...]` is incomplete: rerun with a larger max_rows or a narrower query before concluding that a column, row or value does not exist; `describe` always lists every column.
- `sl` (harness script on PATH) shows the SAGE layer: `sl overview`, `sl models`, `sl model <name>`, `sl sources`, `sl table <schema.table>`, `sl joins [<name>]`, `sl lineage <model>`, `sl search <term>`, `sl values <relation> <column>` (live query), `sl rebuild` (rebuild it after you built models), `sl help`. It describes the projects and the data as found at start.
- `grep -rn "<name>" models macros` finds where something is defined or used; `find models -name '*customer*'` locates files.
- Keep tool output small: use `head`, `tail`, `wc -l`, `LIMIT`.
- After adding a variable or flag that switches logic, build the affected models with each value (`dbt build -s <model> --vars '{name: true}'`, then the configured value).
- Schema and identifier case: DuckDB matches schema names case-insensitively but keeps the case a schema was created with, and dbt compares them case-sensitively. If the warehouse already has a schema in another case (`ANALYTICS` vs `analytics`), the first `dbt run` succeeds but every later run fails with "approximate match". Use the existing case exactly in the profile or schema config (`schema: ANALYTICS`); dropping relations, `quoting` settings or overriding dbt macros do not fix it. Check with `sql "select schema_name from information_schema.schemata"` before choosing a schema name.
